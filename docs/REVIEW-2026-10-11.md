# PulseGames review and development plan

11 October 2026. Initial checkpoint plus the follow-up below; not a production readiness certificate.

## Scope and evidence

Aurora requested broad party, cooperative, racing and competitive coverage, PulseContent-owned custom items/entities with Geyser parity (especially Prop Hunt), and exploration of NPC players at quiet times.

PulseGames was fetched from origin/main at `705d5ac7361fc62887a04328c29a6363806ab508`. It contains **21 games and 43 modes**, all backed by game classes. No open PulseGames PRs existed at the start of this review. Source targets Paper 1.21.4 and Java 21. Installed Minigames server versions, maps and enabled modes were not inspected in this task.

PulseContent's current implementation is in [PulseAddon draft PR 26](https://github.com/PlayerReadyPortsmouth/ReadyCraft-PulseAddon/pull/26), head `0e33e5ce3245c4ec99dbe75bfd61c6d2e6d9cba9`. It targets Paper 26.2 and Java 25. The workspace rollout ledger records a SurvivalTest trial, not a Minigames rollout. The old PulseContent design and Paper README understate the newer entity implementation; the source and encounter example are the better evidence. Real-client guardian acceptance remains pending in that ledger.

## Existing breadth and missing experiences

| Family | Existing games | Meaningful gap |
|---|---|---|
| Party/survival | Party Games, Spleef, TNT Run, Block Party, Avalanche, Volcano, Lucky Pillars | Party Games has only colour rush, sumo and sprint. Add reaction, memory and projectile challenges, with non-repeating rotation and tied-score policy. |
| Competitive | Skywars, Bedwars, Duels, Kit PvP, King of the Hill | Objective carrying, team projectile games and useful small-population practice. |
| Racing | Parkour, Elytra Racing, PulseKarts | Solo practice, personal times, authored route ghosts, fair checkpoint ties; Cup is a lap mode, not a multi-track tournament. |
| Cooperative | Villager Defense, ReadyPlayerZ | Both centre on zombie waves. Non-combat teamwork and objective-driven encounters would add much more variety. |
| Creative/asymmetric | Build Battle, Prop Hunt, Death Run | Stronger plot protection; real prop models and hitboxes; controller-friendly prompts and interactions. |
| Collection | Supermarket Sweep | Reusable item objectives and cooperative delivery mechanics. |

Recommended expansion order, all **proposed, not implemented**:

1. **Dodgeball**: solo/team elimination, limited throws and catches. Short rounds and a bounded first practice opponent.
2. **Dropper**: solo practice and multiplayer stage race, landing regions and retries. Adds low-population play without needing bots.
3. **Bomb Tag**: pass the bomb by a valid hit, visible countdown and round elimination. PulseContent appearance is optional decoration; the server owns possession and timing.
4. **Capture the Flag**: two teams, carried flag, return rules and score cap. Requires an objective lifecycle that handles death, disconnect and dropped flags.
5. **Cooperative delivery/puzzles**: collect, carry and process items at stations against a shared clock. Adds cooperation without more zombie waves; use PulseContent for readable ingredients, packages and station models.

Then deepen current games: richer Party Games rotation, race practice/ghosts, and PulseContent encounter variants. Do not advertise an added game until it has an actual map, setup validation and mixed-client playtest. Existing registered games are not evidence that their production maps work.

A cancelled map clone is reaped by existing empty-lobby cleanup rather than aborted mid-copy.

## PulseContent integration: one content authority

PulseGames should own game rules, round state, roles, scoring and temporary arena entities. **PulseContent should own content IDs, model import, Java/Bedrock packs, registrations, client readiness and model lifecycle.** Do not introduce a second pack generator or locally invented Bedrock mappings in PulseGames.

Current PulseContent provides `createItem(String,int)` and `spawnEntity(String,Location)`. These are useful foundations, but not a complete minigame integration API:

- `createItem` checks active content and the server thread. Per-player Java/Bedrock readiness is currently checked in its give command, not exposed as a supported general capability query. Giving a custom stack to one player also does not prove other viewers can render it.
- `spawnEntity` creates a managed Mythic encounter. It does not attach a harmless prop appearance to a player, return a visual-only handle, or expose per-viewer pack readiness.
- Entity runtime integrates BetterModel 3.5.0, MythicMobs 5.13.0 and GeyserModelEngine. A modeled hostile encounter is not a safe disguise primitive.
- PulseGames and PulseContent currently target different server/Java versions. Resolve the supported Minigames target and compile/run the plugin on it before installation. Do not silently update the production server as part of source changes.
- PulseContent's high-priority death handler adds custom loot after PulseGames' normal handler clears drops. An integration must explicitly suppress encounter loot for game-managed entities; otherwise custom drops can escape the game's intended reward rules.

Required shared API contract (proposal, not shipped API):

- Versioned Bukkit service for content lookup, supported capability reporting and active revision.
- Readiness for each participant/viewer, including late join and reconnect. Required gameplay visuals block admission/start while unavailable; optional cosmetics use an explicit common fallback. Never claim pack acknowledgement alone proves visual correctness.
- Item factory preserving PulseContent identity, plus a temporary visual handle with move/rotate/remove operations and explicit instance ownership.
- Visual-only entity attachment with no inherited encounter AI, attacks or loot. Removal is idempotent, without death effects/rewards, and safe during plugin shutdown/reload.
- Server-side hit ownership, collision and raycast policy shared by Java and Bedrock. Visual bones must not become separate rewarded victims.

### Prop Hunt acceptance slice

Replace the floating helmet with a small catalogue of original props owned by PulseContent. First prove one barrel-like model, then extend the palette. Hiders can move as a prop and lock into place after a visible settling delay. Define one authoritative hit volume for each allowed shape; choose sizes that do not give one client easier hits. Server rules own hide time, seeking, infection and taunt cooldowns.

Keep the actual player body/equipment/name from revealing the role, and test the model from other players' viewpoints. A successful invisible-player potion is insufficient. Route hits on the prop to its owning hider exactly once; reject spectators, other instances, friendly hits and hiding-phase attacks. Test walls/occlusion and moving/locked transitions.

Required playtest matrix: Java seeker → Bedrock hider and the reverse; mixed viewers; hand-held tools; movement/lock/unlock; wrong-prop hit; attack reach; taunts; infection; disconnect; end/force-end; world unload; two simultaneous instances; pack decline/stale revision; proxy reconnect; bridge missing/disabled; no model or loot left in the lobby. Fail admission clearly if required rendering support is unavailable. Keep this mode unavailable until those checks pass.

Upstream documentation confirms custom content needs mappings/packs and that display rendering uses additional translation support. Use the exact selected versions in the proof: [Geyser custom items](https://geysermc.org/wiki/geyser/custom-items/), [Geyser packs](https://geysermc.org/wiki/geyser/packs/), [GeyserDisplayEntity](https://github.com/GeyserExtensionists/GeyserDisplayEntity). These are capability references, not evidence that Minigames already has the required stack installed.

## NPC players at quiet times

Feasible, but not a switch that fills every game. Current rosters resolve UUIDs through `Bukkit.getPlayer()` and `isOnline()`. Teams, inventories, events, statistics and winners all accept Bukkit Players. Putting mob UUIDs in the alive set would create contestants that count toward victory checks but vanish from participant lists.

Introduce a contestant identity with human/bot kind, active/round-out/respawning status, team and score, separated from a human connection. Bot controllers submit the same permitted game actions as humans. Use deterministic behaviour and bounded navigation; no language-model calls in the server tick. PulseContent supplies appearance and equipment, not tactical decisions.

| First candidates | Behaviour | Limits |
|---|---|---|
| Duels/Sumo practice | Approach, stop at reach, delayed attack, edge avoidance | Visible bot label, configurable reaction delay/accuracy, no ranked wins or farmable kill tokens. |
| Dodgeball practice | Aim, throw, dodge and timed catch attempts | Finite ammunition and the same cooldowns/hit rules as humans. |
| KOTH defenders | Navigate between authored waypoints and defend zone | Requires obstacle/stuck handling; bots cannot know hidden players' positions. |
| Race ghosts | Replay recorded/authored routes and show a pace target | A ghost is a practice aid, not a collision-aware competitor or proof of racing AI. |
| Co-op companions | Follow, defend nearby ally, bounded target selection | Keep friendly targeting, revives and rewards explicit. Existing enemy variants are easier than companions. |

Defer universal Bedwars/Skywars builders, freeform Build Battle entrants, kart/elytra race AI and believable Prop Hunt seekers until there is game-specific navigation and fairness work. Prop Hunt seekers must use line of sight, remembered observations and audible taunts, not direct access to the hider UUID list as omniscience.

Quiet-time policy: require at least one human; offer clearly labelled practice/bot-supported modes after a configurable wait; impose per-instance/server bot caps; stop bots when all humans leave; never fill real server slots or pretend bots are online people. Replace bots with arriving humans only at a safe round boundary. Keep bot matches separate from competitive records and make reward eligibility explicit.

[Citizens' API](https://wiki.citizensnpcs.co/API) offers NPC creation and navigation, making it a candidate transport/controller library. It does not implement these game rules or remove the roster assumptions. Verify its compatibility and Bedrock appearance on the chosen target before adopting it; no dependency was installed or purchased in this task.

## Delivery order and verification

1. **Foundation patch** in this branch: queue safety, targeted outcome/combat/landing fixes and regression tests. No new games, custom rendering or bots are claimed shipped.
2. **Remaining safety and rules**: accepted death/reward lifecycle, plot isolation, explicit draw results, race ties, arena validation.
3. **Shared target and PulseContent visual API**: isolated modern Paper/Geyser proof, then Prop Hunt acceptance slice. Reuse PulseContent rather than duplicating it.
4. **Variety batch**: Dodgeball and Dropper with working example arenas; then Bomb Tag and Capture the Flag; then cooperative delivery/puzzles and expanded Party Games.
5. **Quiet-time pilot**: one opt-in practice bot mode, measured performance and human join/leave checks; extend only to games with an actual controller.

Automated tests use JUnit/Mockito and exercise queue cancellation/supersession/party failures, timeout outcomes, cancelled-hit attribution, Elytra FALL routing and Party Games roster combat. They do not simulate a live client or certify Geyser rendering.

Before release, play the affected flows on an isolated Paper server, including slow map loading, /lobby while loading, A→B queueing, disconnect/reconnect, party capacity loss, co-op/race timeouts, tied/leading Duels timeouts, Sumo re-entry and Elytra crashes. On the intended modern target, repeat engine smoke tests across combat, racing, building and co-op. Production migration, pack/bridge installation and server restarts require a separate reviewed rollout.

### Foundation verification, 11 October

`./gradlew test jar` passed: 16 tests, zero failures/errors/skips. The plugin jar compiled against the existing Paper 1.21.4 target. Independent source review found no additional issues in the scoped patch. One earlier test-fixture failure (missing live Paper sound registry) was corrected before this successful run. No live server, Java client or Bedrock client playtest was performed.


### Follow-up implementation, 11 October

Foundation PR #2 merged as `8c1f473` at Aurora's request. No deployment is implied.
The next branch changes the NPC direction from practice-only to normal queue
filling, as explicitly requested. It adds Citizens-backed contestants in Duels,
Kit PvP FFA, KOTH and Dodgeball, with human priority, bounded fill, normal roster
resolution and cleanup, and unranked bot rounds. See [queue bots](QUEUE-BOTS.md).

Dodgeball (three-hit elimination, no catch mechanic) and Dropper (practice/race)
now have opt-in implementations and generated example arenas. This brings the
catalogue to 23 games / 47 modes; it does not certify every existing game or map.
Both are still preview-only pending human client playtests. Broader party and
non-combat co-op expansions in the initial roadmap remain unimplemented.

Death handling now has explicit pending-respawn and re-entry guards and Duels
rejects deaths during round intermissions. KOTH excludes inactive hill occupants.
A general accepted-death result across every older game, Build Battle's wider
mutation protection, persisted draws and Parkour tie ranking remain open.

The companion PulseContent API and Prop Hunt adapter now own player-attached
visual handles and check pack readiness. They do not yet establish Geyser player
disguise parity; see [the precise rendering limits](PULSECONTENT.md). No separate
resource pack or custom entity protocol was added to PulseGames.

Validation: 50 PulseGames unit tests and jar build passed, 10 companion Paper
tests and jar build passed; actual NPC movement/melee/removal and both blueprint
builds passed on a disposable local server. See [verification](VERIFICATION-2026-10-11.md).
No human client, Bedrock client, load or production test was performed.

### Selectable block props follow-up, 11 October

and a half-block player-head option. Companion draft PR27 owns temporary native
